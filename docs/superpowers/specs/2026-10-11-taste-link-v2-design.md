# 品味連結新版、匯出與實際品項：設計規格

- 日期：2026-10-11
- 分支：`feature/taste-traits`
- 範圍：第二段第③輪。新版品味連結（帶品味特質與品項）、打開匯出按鈕、連線圖的「外圈小點」（每個訊號背後最常買的品項）、隱私說明改寫、連線頁煙霧測試，以及幾個順手修。第二段三輪都完成後才合併。
- 依據：[`../handoffs/2026-10-08-taste-traits-stage1.md`](../handoffs/2026-10-08-taste-traits-stage1.md) 第②輪的「第③輪要記得」第 1～4 項、第①②輪的「已知、暫不處理」，以及同一份文件「第二段第③輪」記下的討論決定。
- 取代：
  - [`2026-10-09-trait-network-design.md`](2026-10-09-trait-network-design.md) §5「三種情況」表中「朋友比較：有一側是貼上的連結」那一列：新版連結有品味特質時可以畫圖。
  - 同一份規格 §5「配對資料改由連線頁計算分數」的 `traits`：多帶 `items`。
  - 同一份規格 §8「嵌入的資料仍不含任何店名或品名」：改成不含店名與行政區；品名只出現在品項清單裡，而且已套用本規格 §2 的品名規則。

## 目標

把自己的品味帶出報告：按「匯出我的品味連結」得到一個連結，朋友貼上後就能看到兩人的品味特質連線圖與品味相似度。連線圖上每個訊號背後是真的買過的東西：點一個訊號，外面長出最常買的品項，看得出「買了什麼」，但看不出在哪裡買。

## 已確認的決策

| 項目 | 決定 |
|---|---|
| 範圍 | 「第③輪要記得」第 1～4 項＋實際品項＋順手修（§9）。第 5 項真實資料校準之後再做 |
| 金額訊號 | 連結帶 `meal_cost`（每餐花費）與 `tech_spend`（3C 花費），說明照實寫。推力配上 `configs/traits.json` 就能算回金額（示範的「我」每餐 NT$125、3C 每月 NT$780，誤差不到 1 元），不帶只是把數字藏起來 |
| 實際品項的畫法 | 「外圈小點」：小點（訊號）保留，點一個訊號時，兩側同一個訊號外面各長出最多 3 個品項點 |

| 資料來源 | 品項清單和品味特質一樣由 Python 算好嵌入，瀏覽器只檢查、畫圖、編成連結 |
| 新版連結 | `receipt-taste/traits-v2`：舊版欄位＋品味特質（向量、推力、訊號、品項）；舊版連結照常可讀 |
| 匯出面板 | 照實的隱私說明；列出「朋友會看到這些品名」，分享前可以檢查 |
| 示範兩字 | 品名開頭的「示範」在嵌入網頁時就省略，原始示範資料不變 |

## 1. 每個訊號背後的消費（Python）

### `signals.measure` 多回傳 `purchases`

`measure` 在算每個訊號時，用同一批中間資料記下「算進這個訊號的消費」，回傳 `{訊號 id: [消費明細, …]}`（明細是 `gather` 產生的 line，只在 Python 裡用，不嵌入網頁）。訊號量不到（值是 `None`）時清單為空。

| 訊號 | 算進來的消費（都是 `valid_items` 裡的品項） |
|---|---|
| meal_cost | 算進每餐花費的發票上的正餐 |
| clearance_share | 有即期字樣的食物 |
| premium_drink_share | 單價 100 元以上的飲品 |
| store_meal_share | 超商的正餐 |
| weekday_quick_share | 工作日、成為習慣（3 個工作日以上）的速食正餐 |
| store_clearance_share | 超商的即期食物 |
| shop_meal_share | 不在超商、量販、超市的正餐 |
| fresh_share | 下廚用的生鮮 |
| ready_meal_share | 正餐 |
| kitchen_per_month | 廚房用品 |
| sugar_mean | 看得出甜度的飲品 |
| dessert_share | 甜點 |
| repeat_rate | 同一個月買過 2 次以上的品名 |
| sport_visits | 運動類品項 |

| fuel_visits、parking_visits、stays、long_trips、select_visits、tech_visits、bar_visits | 該通路發票上的品項（加油、停車、住宿、長途交通、選物、3C、酒吧） |
| convenience_share | 超商發票上的日用品（只算有日用品的超商、量販發票中，超商那些） |
| bulk_share | 大包裝的日用品 |

| fun_visits、fun_kinds | 有娛樂種類的品項 |

| pet_visits_* | 歸給該物種（或看不出物種）的寵物店發票上的品項 |
| away_share、shop_focus、new_shop_share、holiday_trip_share | 不列（算的就是地點或店家） |

### 品名規則（新檔 `src/receipt/items.py`）

每一筆消費先決定顯示的名稱（label），規則依序套用，**不論它出現在哪個訊號的清單**（住宿品項出現在「假日消費」清單裡，也只寫「旅館住宿」）：

1. 去掉開頭的「示範」。
2. **住宿**：通路是「住宿」的消費，一律寫 `旅館住宿`。
3. **長途交通**：通路是「長途交通」的消費，依品名與店名找交通方式：高鐵 → `高鐵票`、臺鐵（含自強、莒光、區間）→ `臺鐵票`、客運（含巴士）→ `客運票`、航空（含機票、航班）→ `機票`；都不符合寫 `長途交通票`。
4. **其他品名只拿掉地名**，其他字保留：`台中油飯` → `油飯`。地名包括：
   - 22 個縣市的全名與去掉「市／縣」的簡稱（`address.py` 的 `MUNICIPALITIES`、`COUNTIES`），以及縣轄市（`COUNTY_CITIES`）的全名與簡稱；
   - 這個人發票上出現過的行政區：去掉縣市後的全名（`苓雅區`），以及再去掉「區／鄉／鎮／市」、仍有 2 個字以上的簡稱（`苓雅`）；
   - `configs/attributes.json` 新增的 `place_words`（例如淡水、鹿港、九份、墾丁）。

   比對時「台」「臺」視為相同。拿掉後去除頭尾的空白與標點；若沒有剩下中文字或英文字母，改寫成該品項的類別名稱（`configs/report.json` 的分類名，例如「正餐」）。
5. 連鎖品牌不處理，照常顯示（`星巴克那堤`）。
6. 超過 20 個字時截成 19 個字加「…」。

### 品項清單

`items.listed(purchases, rows, settings, context)` 回傳 `{訊號 id: 清單或 None}`：

- 設定中標為 `"list_items": false` 的訊號是 `None`。
- 其他訊號：依顯示名稱合併，次數 = 這個名稱出現在幾張不同的發票上；依次數由多到少、同樣多時依名稱（程式碼點順序）排序，取前 3 個，寫成 `[[名稱, 次數], …]`；沒有消費時是 `[]`。

`traits.explain` 的結果多一個 `items`（上面的字典）。`population` 照舊。

### 設定

- `configs/traits.json`：`away_share`、`shop_focus`、`new_shop_share`、`holiday_trip_share` 加 `"list_items": false`。重複出現的訊號，兩處的 `list_items` 必須相同（同 `label`、`unit` 的規則）。
- `configs/attributes.json` 新增：
  - `"transport_kinds"`：`[[顯示名稱, [關鍵字…]], …]`，依序比對，第一個符合的勝出；
  - `"place_words"`：地名清單，初始內容在計畫中決定；
  - `"generic_labels"`：`{"住宿": "旅館住宿", "長途交通": "長途交通票"}`（長途交通是找不到交通方式時的寫法）。
- `traits.load_context` 多讀 `configs/report.json`（分類名稱），供規則 4 的類別名稱使用。

## 2. 嵌入網頁的資料

品項清單依 `signal_ids` 的順序排成陣列，和 `signals` 對齊；每格是 `null`（不列品項的訊號）或 `[[名稱, 次數], …]`（0～3 個）。

| 位置 | 內容 |
|---|---|
| 主頁（新） | 新的嵌入常數 `tasteExportData = {"traitCount": 17, "taste": {vector, pushes, signals, items} 或 null}`。`src/web/invoice-insights.html` 在 `taste-export.js` 前加 `<script src="taste-export-data.js"></script>`，由 `build.py` 嵌入。`traitCount` 依 `group` 規則算（同 `TraitNetwork.traitCount`）；`vector` 完整精度，`pushes`、`signals` 四捨五入到小數 4 位，與配對頁相同 |
| 配對頁 `matchReportData` | `me` 與每位 `people[]` 多一個 `items` |
| 連線頁 `traitNetworkData` | `friends` 每位多一個 `items`；`signals` 中不列品項的訊號帶 `"list_items": false` |
| 配對頁傳給連線頁的 `pair` | `traits: {vector, pushes, signals, items}` |

- 「我」資料不足時，`tasteExportData.taste` 與 `matchReportData.me` 的 `items` 都是 `null`。
- **大小**（試算）：配對頁資料多約 28 KB，報告從約 277 KB 變成約 310 KB，仍是單一 HTML 檔。

## 3. 新版品味連結

### 格式

```text
{
  "schema": "receipt-taste/traits-v2",
  "name":   暱稱（1～24 字）,
  "demo":   true/false,
  "months": ["2026-03", "2026-04"],
  "counts": 10 類筆數（品項細節要用）,
  "traits": {vector, pushes, signals, items} 或 null（資料不足）
}
```

- 和舊版一樣用 base64url 放在網址的 `#taste=` 後面；連結長度上限 12,000 字元不變。示範的「我」約 2,300 字元。
- 匯出一律產生新版。舊版 `receipt-taste/categories-v1` 照常可讀。

### `TasteProfile`（`taste-profile.js`）

- `validate` 接受兩種版本。新版的 `traits` 必須是 `null` 或物件，原樣保留（深入檢查交給連線頁的 `TraitNetwork.validate`）；其他欄位的檢查與重建方式不變。
- `fromReport(report, name, taste)` 產生新版，`traits` 是 `taste`（沒有時為 `null`）。
- `toURL`、`fromURL`、`fromPair` 的介面不變。

### 收緊 `TraitNetwork.validate(person, data)`

不合格就拋出錯誤；錯誤訊息由呼叫的頁面決定（配對路徑照舊退回清單，朋友比較頁見 §5）。合格時回傳新的副本 `{vector, pushes, signals, items}`。

- **向量**：長度等於特質數；每格是 `null`，或在 −1～+1（程度型 0～1）的有限數字。（不變）
- **推力**：列數等於特質數，每列長度等於該特質的訊號數；每格是 `null`，或在 −1～+1（程度型 0～1）的有限數字。
- **空的規則**：特質是 `null` 時，那一列推力全是 `null`；訊號值是 `null` 時，它在每項特質的推力都是 `null`。
- **加總**：特質不是 `null` 時，那一列非 `null` 推力的總和與特質值相差不超過 0.001。
- **訊號**：長度等於訊號數；每格是 `null`，或 0～1,000,000 的有限數字。
- **品項**：長度等於訊號數；`list_items` 為 `false` 的訊號必須是 `null`，其他訊號必須是最多 3 筆的陣列；每筆是 `[名稱, 次數]`，名稱是去掉頭尾空白後 1～20 字、不含控制字元的字串，次數是 1～10,000 的整數；同一個訊號裡名稱不重複。

### 貼上連結時（朋友比較頁）

| 貼上的是 | 結果 |
|---|---|
| 新版連結，兩邊都有品味特質 | 品味特質圖、大字分數、外圈小點都有 |
| 新版連結，`traits` 是 `null` | 只能看品項細節；按鈕旁「這份連結的資料還不夠算出品味特質」；大字下方「這份連結的資料還不夠，無法計算品味相似度」 |
| 舊版連結 | 照現在：按鈕旁「這份連結還沒有品味特質」；大字下方「舊版連結沒有品味特質，無法計算品味相似度」 |
| `traits` 檢查不合格 | 拒收，匯入狀態寫「連結裡的品味特質不正確，請對方用新版報告重新匯出。」，後面照現在接「圖中仍保留…的資料。」 |
| 只有一邊有資料 | 按鈕旁「另一邊匯入後才能看品味特質」 |

- 兩邊都有問題時，說明以左側為準。
- 連線頁單獨打開（不在報告裡，沒有 `traitNetworkData`）時，新版連結也只看品項細節，與現在相同。

## 4. 連線圖的外圈小點

畫圖的位置由 `trait-network.js` 的純函式算好，`taste-comparison.html` 只負責畫成 SVG 與處理點選。

### 什麼時候出現

| 情況 | 做法 |
|---|---|
| 點一側的訊號（滑鼠，或 Tab 後按 Enter／空白鍵） | 兩側同一個訊號外面各長出它的品項點；某一側清單是空的就只有另一側 |
| 點特質或中間的線 | 不長品項點，照現在亮起整條路 |
| 滑過訊號 | 照現在只顯示訊號名稱 |
| 取消選取（點空白處、Esc、「顯示全部連線」）或改點別的 | 品項點消失 |

### 畫法

- **位置**：品項點放在訊號點沿著扇面方向再往外的地方，3 個品項在訊號的方向兩側平均展開；標籤放在品項點外側（桌機左團靠右對齊、右團靠左對齊；手機依品項點在訊號的左或右）。
- **大小與粗細**：品項點的大小與連到訊號點的直線粗細，都依次數，和同一個清單裡最多的那個比。顏色是那一側的顏色，品項點半透明填色。
- **標籤**：`名稱 ×N`。名稱超過 10 個字時，圖上截成 9 個字加「…」；說明列寫全名。
- **訊號名稱**：展開品項時，釘在訊號點旁的名稱改放到內側，把外側留給品項。
- **預留空間**：品味特質圖的 `viewBox` 四周固定留白，大到放得下最長的標籤（10 個字＋「 ×N」）在任何一個訊號旁，點選時不縮放。試做時桌機整張圖約小 16%。
- **確切數值**（往外的距離、展開角度、點大小、留白）在計畫中用示範資料試畫後決定，寫進 `SHAPES`。
- **無障礙**：品項點與標籤是裝飾（`aria-hidden`），不能用 Tab 選到；品項寫在說明列（`role="status"`），螢幕閱讀器會念出來。

### 說明列

訊號的那一行在訊號值後面加上品項：

- 有品項：「你：飲料甜度 約 8 分糖（半糖冬瓜青茶 ×7、百香果茶 ×7、花果茶 ×7），往「高甜度」推 0.61」
- 不列品項的訊號：「你：常去店家 29%（這個訊號不列品項），往「喜歡嘗鮮」推 0.30」
- 清單是空的：照現在，不加括號。

### 圖例

品味特質圖例加一項「外圈：常買的品項（點小點出現）」。

## 5. 朋友比較頁（`taste-comparison.html`）

- **匯入**：`importProfile` 讀到新版連結時，`traits` 是物件就用 `TraitNetwork.validate(traits, network)` 檢查，結果與「沒有品味特質的原因」（舊版／資料不足）存進該側資料，供 §3 的各種說明使用。
- **按鈕說明**：品味特質按鈕停用時一定顯示原因（§3 表格）。
- **示範朋友**：載入 `traitNetworkData.friends` 時 `validate` 包在 try/catch 裡；某位不合格時只有他沒有品味特質，整頁照常。
- **資料來源說明**（「資料來源與相似百分比怎麼算？」）：
  - 新增連結說明段，有一側是貼上的連結時顯示（兩種畫面都顯示）：「品味連結包含暱稱、涵蓋月份、10 類已確認消費品項的筆數、17 項品味特質、各消費訊號的彙總值（例如每餐平均花費、每月 3C 花費、每月次數），以及每個訊號最常買的品名；不包含店名、行政區、地址、日期、單筆金額或發票號碼。品名裡的地名已拿掉，住宿只寫「旅館住宿」。舊版連結只有暱稱、月份與 10 類筆數。拿到連結的人都讀得到這些內容；編碼並非加密。」原本品項細節裡的第一段（「報告連結包含暱稱……」）刪除。
  - 品味特質說明拆成兩段：「品味相似度是 N 項品味特質（M 格）的餘弦相似度……」兩種畫面都顯示；講訊號線、中間的線的句子，加上新的一句「點一個訊號，外圈會出現最常買的品項（最多 3 個，×N 是整段期間的次數）；外地消費、連假出遊、常去店家、新店家這 4 個訊號不列品項。」只在品味特質畫面顯示。
- 「17 項」「4 個訊號」與訊號名稱都由設定產生。

## 13. 風險

- **品名規則抓不到的情況**：單一店家的名字寫在品名裡（例如「阿明招牌麵」）、不在清單裡的地名，規則都認不出來；縣市簡稱也可能誤拿掉別的詞的一部分（例如「新北投」）。匯出面板列出所有會分享的品名讓使用者檢查；真實資料階段要再人工確認。
- **圖變小**：為了點選時不縮放，桌機整張圖約小 16%。
- **報告變大**：約 277 KB → 310 KB。
- **不同版本的設定**：朋友的報告若用了不同的 `traits.json`，格數不同會被拒收；格數相同但順序不同時無法察覺。
- **次數的寫法**：說明列的「每月 5 次」與外圈的「×10」（兩個月合計）並列，可能讓人以為不一致；圖上的說明寫明 ×N 是整段期間的次數。
- **煙霧測試的範圍**：假 DOM 只檢查主要流程與關鍵文字，排版仍靠最終的瀏覽器實測。
