# 消費標籤與同好配對：設計規格

- 日期：2026-10-07
- 分支：`feature/tags-matching`
- 範圍：規劃清單的 1（補資料欄位）、2（產生用戶標籤）、3（配對演算法），以及一個簡單的配對頁

## 目標

從發票明細產生「消費標籤」，再和一群虛構用戶比較，找出品味相近的人，並說明為什麼相近、哪裡不同。整個流程用虛構資料就能示範，公開示範版不讀取任何私人消費紀錄。

## 已確認的決策

| 項目 | 決定 |
|---|---|
| 地點放進網頁的程度 | 每筆明細帶「縣市＋區」；完整地址與統編不放進網頁 |
| 標籤面向 | 品類偏好、生活圈、常去品牌、消費檔次、口味（葷素） |
| 計算位置 | Python 在產生報告時算好，網頁只顯示結果 |
| 畫面 | 新增簡單的配對頁，從報告頁連過去 |
| 品牌對照 | 公開設定檔放常見連鎖品牌關鍵字，示範版與私人版共用 |
| 推薦門檻 | 品味分數（不含生活圈）至少 60%，且總分至少 50% |

## 架構與資料流

```text

示範資料 ──> demo.py ─────┤            (公開版)
                          ▼
                  每月明細（含 district）
                          │
          ┌───────────────┼──────────────────┐
          ▼               ▼                  ▼
     報告頁（既有）    tags.py：我的檔案     personas.py：40 位虛構用戶
                          │                  │

                                   │
                                   ▼
                   配對結果（我的標籤、前 5 名、理由、差異）

```

## 1. 補資料欄位

### 地址解析（`address.py`）

`parse_district(address) -> str | None`，回傳例如 `高雄市苓雅區`，無法解析時回傳 `None`。

1. 正規化：移除所有空白（含全形空白 `　`）、開頭的郵遞區號數字，並把「台」改成「臺」。
2. 開頭比對 22 個縣市名稱。
   - 直轄市與市（臺北市、新北市、桃園市、臺中市、臺南市、高雄市、基隆市、新竹市、嘉義市）：取最短的 1–3 字加「區」。
   - 縣：取最短的 1–3 字加「鄉、鎮、市」其中之一。
   - 縣市後面找不到區名時，回傳 `None`。
3. 開頭若是縣轄市而沒有縣名，補上縣名：竹北市→新竹縣、苗栗市與頭份市→苗栗縣、彰化市與員林市→彰化縣、南投市→南投縣、斗六市→雲林縣、太保市與朴子市→嘉義縣、屏東市→屏東縣、宜蘭市→宜蘭縣、花蓮市→花蓮縣、臺東市→臺東縣、馬公市→澎湖縣。
4. 其他情況回傳 `None`。

### 明細欄位

- `invoices.py`：每筆明細新增 `district`（字串或 `null`）。完整地址與統編仍不保存。
- `demo.py`：每家示範店家指定一個真實的行政區，店名維持虛構。
- 報告頁明細表新增「行政區」欄，`null` 顯示為「未知」。
- 頁尾說明改為：「頁面只保留匿名發票代碼與行政區，不嵌入原始號碼、統編或完整地址。」

## 2. 用戶標籤（`tags.py`）

### 計算基礎

- **有效品項**：金額大於 0、分類已確認（非暫定）、分類為前 10 類的明細。規則和朋友比較頁的品味連結相同。
- **發票**：以發票代碼分組，發票金額為同張所有明細的加總（含折扣）。金額大於 0 的發票才計入。
- 一張發票的行政區與品牌，由該張發票的賣方決定。

### 標籤定義

| 標籤 | 計算方式 | 顯示例子 |
|---|---|---|
| 品類偏好 | 有效品項依分類計數，取占比前 2 名 | 常買飲品（31%） |
| 生活圈 | 依發票張數排序行政區，取前 2 名，每區至少 2 張；未知區不計 | 生活圈：高雄市苓雅區 |
| 常去品牌 | 依品牌表比對賣方名稱，出現 3 張以上的品牌 | 常去：7-ELEVEN（12 次） |
| 消費檔次 | 發票金額中位數：未滿 150 元為小資型，150 至未滿 400 元為均衡型，400 元以上為享受型 | 均衡型 |
| 口味 | 見下方「口味（葷素）」 | 偏蔬食 |

所有門檻、級距與文字都放在 `configs/tags.json`。

### 品牌對照（`configs/brands.json`）

比對前，賣方名稱與關鍵字都先把「台」改成「臺」。只要賣方名稱包含任一關鍵字，就算該品牌。對不到的店家不列入品牌計算，因為小店比連鎖店更容易定位到個人。

|---|---|

| 超市量販 | 全聯（全聯實業）、家樂福（家福股份有限公司、家樂福）、好市多（好市多）、大潤發（大潤發）、美廉社（三商家購） |
| 咖啡 | 星巴克（統一星巴克）、路易莎（路易莎） |
| 速食烘焙 | 麥當勞（麥當勞、和德昌）、摩斯漢堡（安心食品）、85度C（美食達人） |
| 藥妝生活 | 屈臣氏（屈臣氏）、康是美（統一生活事業）、寶雅（寶雅國際）、無印良品（無印良品） |
| 3C | 燦坤（燦坤）、全國電子（全國電子） |

### 口味（葷素）

- 只看分類為正餐、飲品、零食甜點、生鮮食材的有效品項。
- 品名含葷食詞 → 葷（1）；否則含素食詞 → 素（0）；都沒有 → 不計入口味。
  - 葷食詞：豬肉、牛肉、雞肉、雞腿、雞排、雞塊、雞柳、羊肉、鴨肉、鵝肉、鮮蝦、蝦仁、鮭魚、鯛魚、鮪魚、鱈魚、魚排、海鮮、排骨、培根、火腿、肉燥、肉絲、肉片、肉鬆、香腸、叉燒、燒肉、滷肉、魯肉、牛排、豬排
  - 素食詞：素食、蔬食、全素、蛋奶素、蔬菜、素餃、素料、素肉
  - 只用兩字以上的詞，避免「牛奶」「肉桂捲」被誤判。
- 偏葷程度＝葷品項數 ÷ 有口味的品項數。有口味的品項少於 3 個時，不產生口味標籤。
- 標籤：偏葷程度 0.3 以下為「偏蔬食」，0.7 以上為「偏葷食」，其餘為「葷素都吃」。

### 個人檔案結構

```python
{
  "category_counts": [int] * 10,
  "district_shares": {"高雄市苓雅區": 0.6, ...},
  "brand_shares": {"7-ELEVEN": 0.5, ...},
  "price_level": 0 | 1 | 2 | None,
  "meat_ratio": float | None,
  "flavor_items": {"示範水餃館": {"示範蔬菜水餃": 4}, ...},
  "tags": [{"dimension": "生活圈", "text": "高雄市苓雅區"}, ...],
}
```

- `flavor_items` 依品牌記錄有口味的品名與次數，用來產生同店差異說明。
- 一個面向的資料量不足（行政區、品牌或發票少於 3 張；口味品項少於 3 個）時，該面向的值為 `None` 或空集合。

## 3. 配對（`matching.py`）

### 各面向相似度（0 到 1）

| 面向 | 算法 | 權重 |
|---|---|---|
| 品類 | 兩人品類筆數的餘弦相似度 | 0.35 |
| 生活圈 | 行政區占比的交集：每區取兩人較小的占比後加總 | 0.30 |
| 品牌 | 連鎖品牌占比的交集，算法同生活圈 | 0.15 |
| 口味 | 1 −｜兩人偏葷程度的差｜ | 0.10 |
| 消費檔次 | 同級為 1，差一級為 0.5，差兩級為 0 | 0.10 |

- 任一方缺少某面向的資料時，該面向不計分，其他權重依比例放大。
- **品味分數**：只用品類、品牌、口味、消費檔次，不含生活圈。
- **總分**：五個面向全部加權。
- 權重放在 `configs/tags.json`。

### 推薦門檻與排序

- 品味分數至少 60%，**且**總分至少 50%，才會被推薦。只靠住在同一區無法通過。
- 依總分由高到低排序，同分時比較品味分數，再比較名稱。
- 最多列 5 名；沒有人通過時，配對頁顯示「目前沒有夠相似的人，多掃幾張發票再看看」。
- 門檻預設 60% 與 50%，實作時用虛構用戶的分數分布校準；如需調整，先和使用者確認。

### 配對理由（最多 3 條）

只列兩人確實重疊的部分，依該面向的「權重 × 相似度」由高到低選：

- 生活圈標籤有重疊：「都常在高雄市苓雅區消費」
- 常去品牌有重疊：「都常去示範茶屋」
- 品類前 2 名有重疊：「都很常買飲品」
- 口味標籤相同：「口味都偏蔬食」
- 消費檔次相同：「消費檔次都是均衡型」

一條都沒有時顯示「整體消費比例相近」。

### 差異說明

兩人都有口味資料，且偏葷程度相差 0.6 以上時，加一條差異說明：

- 兩人有共同常去品牌，且在該品牌各有口味品項：「都常去示範水餃館，但點的不一樣（示範蔬菜水餃／示範鮮蝦水餃）」，各取在該品牌最常買的口味品項。
- 否則：「口味不同：一位偏蔬食、一位偏葷食」。

## 4. 虛構用戶（`personas.py`）

- 以固定亂數種子產生 40 位虛構用戶，每次結果相同。
- 8 種類型，每種 5 位：咖啡上班族、手搖學生、健身族、自己下廚、3C 玩家、旅行族、零食夜貓、家庭採買。
- 每種類型設定偏好的品類、行政區、連鎖品牌、品項（部分品名帶葷素詞）與發票金額範圍；同類型成員之間有隨機差異。
- 每人 2 個月的明細，欄位與報告明細相同。
- 名稱寫出類型，例如「咖啡上班族 A」，避免像真人。
- 其中刻意安排：
  - 同一示範連鎖店、一位偏蔬菜水餃、一位偏鮮蝦水餃的組合，用來展示差異說明。
  - 至少 1 位和示範版的「我」同區、但品味完全不同，用來展示門檻。
- 示範版的「我」是現有的虛構示範資料；私人版的「我」是使用者本人的資料。兩者都和這 40 位配對。

## 5. 配對頁（`match.html`）

- 報告頁上方「比較跟朋友品味差多少」旁，新增「找到同好 ↗」連結（`#match`）。
- 沿用朋友比較頁的做法：配對頁原始碼以 `<template>` 嵌入報告檔，切到 `#match` 時才載入到 iframe。`taste-navigation.js` 擴充為可切換兩個頁面。報告仍是可離線開啟的單一檔案。
- 頁面內容：
  1. 返回消費洞察的連結、標題、說明「配對對象皆為虛構示範用戶」。
  2. 我的標籤卡。
  3. 配對前 5 名：名稱、總分、品味分數、對方標籤、配對理由、差異說明。
  4. 可展開的「怎麼算的」：面向、權重、門檻，以及「只用行政區與連鎖品牌，不顯示分店、日期或金額」。
- 嵌入的資料只有計算結果：我的標籤、通過門檻者的標籤與文字。虛構用戶的明細不放進網頁。
- 顯示文字一律用 `textContent` 寫入，不用 `innerHTML` 插入資料。

嵌入資料格式：

```json
{
  "isDemo": true,
  "candidates": 40,
  "settings": {
    "weights": {"category": 0.35, "district": 0.3, "brand": 0.15, "flavor": 0.1, "price": 0.1},
    "thresholds": {"taste": 0.6, "total": 0.5}
  },
  "me": {"tags": [{"dimension": "品類偏好", "text": "常買飲品（31%）"}]},
  "matches": [
    {"name": "咖啡上班族 A", "total": 78, "taste": 82,
     "tags": [{"dimension": "生活圈", "text": "臺北市信義區"}],
     "reasons": ["都常去示範茶屋"], "differences": []}
  ]
}
```

`settings` 直接取自 `configs/tags.json`；`total` 與 `taste` 為四捨五入後的百分比整數。

## 7. 測試計畫

Python（`unittest`，全部使用虛構資料）：

- `address`：郵遞區號、台與臺、全形空白、直轄市與縣的區名結尾、縣轄市補縣名、無法解析。
- `invoices`：明細多出 `district`；完整地址與統編不在輸出中。
- `tags`：各標籤門檻、暫定分類與折扣排除、品牌比對（含台與臺）、中位數級距、資料不足時不產生標籤。
- 口味：「牛奶」「肉桂捲」不算葷；同時有葷素詞時算葷；口味品項少於 3 個時不計。
- `matching`：各面向數值、缺資料時重新分配權重、兩道門檻、排序、理由與差異說明。
- `personas`：結果可重現；每位用戶不套門檻時的第 1 名都是同類型；同店不同餡的組合會產生差異說明；同區但品味不同的用戶不會被推薦給示範的「我」；示範的「我」至少有 1 位推薦。
- 產生報告：配對頁有嵌入、沒有外部資源、不含完整地址與統編、重複產生結果相同。

Node：現有測試全部通過；`taste-navigation.js` 的修改不影響朋友比較頁。

## 8. 不在這次範圍

- README 與簡報更新（1–3 完成後另外處理）。
- 時間節奏標籤（發票只有日期，且已決定不做）。
- 甜度、辣度（發票品名很少出現）。
- 後端、帳號、真實用戶之間的配對。

## 9. 風險

- **門檻**：品類分布在人與人之間本來就相似，餘弦相似度可能偏高，60% 可能太寬鬆。實作時用虛構用戶校準，再確認。
- **品牌名稱**：品牌表只放有把握的公司名稱，仍可能有遺漏或改名，可自行增補。
- **口味詞典**：關鍵字判斷會有漏判，例如「高麗菜水餃」沒有標示葷素。之後做分類模型時，可以一併改善。
