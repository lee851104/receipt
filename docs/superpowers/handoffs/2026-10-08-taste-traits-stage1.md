## 與計畫不同的地方

審查時發現計畫原文的問題，修正後的程式與計畫不同。測試因此是 78 個，比計畫寫的 74 個多 4 個。

1. **沒有生活圈就不算出遊日**：若沒有任何行政區達到發票的 20%，就不把任何發票算成外地。原本每次消費都會變成出遊日，讓不出門的人在「避開連假」拿到 −1。（`signals.measure`）
2. **沒有月份時回報資料不足**：期間為空時，`traits.build_vector` 回傳 `None`，不再除以零。
3. **寵物**：狗零食、貓零食算寵物食品；寵物通路的發票只依寵物品項（食品或用品）分貓狗，符合規格 §2 第 16 項。規格 §1「寵物食品」一格已同步更新。
4. **數量 0 的飲品當 1 份計價**，不再除以零。
5. **私人版測試**加上「終端輸出不含店名」的檢查。

## 第二段合併前必做

1. **瀏覽器版要驗證匯入的向量**：`TraitSimilarity.compare` 目前在向量長度和模型不符時會算出 `NaN`（`undefined` 被當成有值）。讀取新版品味連結的地方要檢查長度與模型相同、每格是 `null` 或 −1～+1 之間的有限數字。
2. **`taste_summary` 要回傳朋友的相對向量**：規格 §5 要算小安、小宇、小林的相對向量，目前只算出原始向量就丟掉。另外，原始向量用名字當鍵，朋友若和虛構用戶同名會互相覆蓋。建議和中間點一起回傳，並與 `tests/test_personas.py` 共用同一個輔助函式。

## 設計第二段時要知道的

- **每格貢獻**：`compare` 的 `parts` 可直接用於「特質 → 相似度」的連線。若要畫「訊號 → 特質」，`traits.trait_value` 目前不回傳各訊號的貢獻；而且相似度用的是減去中間點後的相對值，圖上要多一個中間點項才能讓數字加總一致。
- **中間點的樣本**：「避開連假 ↔ 連假出遊」的中間點 +0.20 只由 5 位連假旅人算出，其他人這格沒有值；「超商：省錢 ↔ 省時」也只來自有足夠超商紀錄的人。校準推薦門檻時要考慮。
- **虛構用戶的亂數**：40 人共用一個亂數序列，改任何一類的習慣，排在後面的人都會重新抽。目前邊界最薄的是省錢上班族與忙碌工程師的超商正餐比例最低 0.827（門檻 0.8），以及忙碌工程師程度型分歧 0.949 對 0.920。
- **娛樂種類**依 `configs/attributes.json` 的順序取第一個符合的，所以「示範遊樂園門票」目前歸為展演而不是遊樂。數值不受影響，做標籤前要決定優先順序。
- **Python 與瀏覽器的加總**：Python 3.12 的 `sum()` 會做補償加總，瀏覽器是逐項相加，差距在 4.4e-16 以內（規格容許 1e-9），目前沒有任何百分比不同。若同一組分數兩邊都會顯示，可把 Python 改成逐項相加。
- **百分比**一律用 `similarity.percent` 或 `TraitSimilarity.percent`。中位數目前取排序後第 `len // 2` 個，人數為偶數又需要精確時改用 `statistics.median`。
- **移除舊程式**：刪除 `tags.py`、`matching.py` 時，`signals.py` 的有效品項規則（同一張發票的同一品名只算一次）是從 `tags.py` 複製來的，刪掉後就只剩這一份。

## 真實資料

- 原始發票匯出檔放在專案根目錄（`*.csv`），被 `.gitignore` 排除，不在 Git 裡；換電腦時要另外複製。
- `data/private/report.json` 與私人品項對照表目前都不存在，所以真實品項全是「待確認」，真實的品味向量是資料不足。要做真實資料校準，先照 README「若要重新產生自己的報告」那段說明，建立 `data/private/report.json` 與對照表。
- 私人 `report.json` 的分類順序必須和 `configs/report.json` 相同，因為 `attributes.py` 直接用分類編號。
- 已知的關鍵字誤判（規格 §7 把真實資料驗證列為之後的工作）：
  - `Bar` 會比對到 Barista。
  - 「中油」會把「台中油飯」當成加油站。
  - 「料理清酒」「紅酒燉牛肉」會被算成酒。
  - 單字「箱」「組」會誤抓。
  - 動物醫院帳單若只有服務品項，貓狗各算一半。
