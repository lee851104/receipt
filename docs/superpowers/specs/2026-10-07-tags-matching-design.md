# 消費標籤與同好配對：設計規格

- 日期：2026-10-07（同日依審查意見修訂：資料門檻、生活圈確認、葷素規則、多人消費）
- 分支：`feature/tags-matching`
- 範圍：規劃清單的 1（補資料欄位）、2（產生用戶標籤）、3（配對演算法），以及一個簡單的配對頁

## 目標

從發票明細產生「消費標籤」，再和一群虛構用戶比較，找出品味相近的人，並說明為什麼相近、哪裡不同。整個流程用虛構資料就能示範，公開示範版不讀取任何私人消費紀錄。標籤描述的是購買紀錄，不直接認定本人的生活圈或飲食習慣。

## 已確認的決策

| 項目 | 決定 |
|---|---|
| 地點放進網頁的程度 | 每筆明細帶「縣市＋區」；完整地址與統編不放進網頁 |
| 標籤面向 | 品類偏好、常消費地區、常去品牌、消費檔次、葷素紀錄 |
| 計算位置 | Python 在產生報告時算好分數；網頁只依使用者確認的生活圈套用門檻 |
| 畫面 | 新增簡單的配對頁，從報告頁連過去 |
| 品牌對照 | 公開設定檔放常見連鎖品牌關鍵字，示範版與私人版共用 |
| 資料門檻 | 品類必須可比較（有效品項至少 10 筆），且至少再有品牌、葷素紀錄、消費檔次其中一項；不足時顯示「資料不足」 |
| 生活圈 | 依地址推測的只叫「常消費地區」；使用者在配對頁勾選確認後，才算生活圈 |
| 推薦門檻 | 品味分數（不含地區）至少 80%；和對方的地區有重疊、且該地區經使用者確認為生活圈時，放寬為 70% |
| 葷素判斷 | 明確素食詞優先，其次葷食詞，其餘為未知；「蔬菜」不算素食證據 |
| 多人消費 | 同一張發票的同一品名只算一次；有品項買 2 份以上的發票不列入消費檔次 |

## 1. 補資料欄位

### 地址解析（`address.py`）

`parse_district(address) -> str | None`，回傳例如 `高雄市苓雅區`，無法解析時回傳 `None`。

1. 正規化：移除所有空白（含全形空白）與開頭的郵遞區號數字，「台」改成「臺」，再去掉開頭的「臺灣省」或「臺灣」。
2. 開頭比對 22 個縣市名稱。
   - 直轄市與市（臺北市、新北市、桃園市、臺中市、臺南市、高雄市、基隆市、新竹市、嘉義市）：取最短的 1–3 字加「區」。
   - 縣：取最短的 1–3 字加「鄉、鎮、市」其中之一。
   - 縣市後面找不到區名時，回傳 `None`。
3. 開頭若是縣轄市而沒有縣名，補上縣名：竹北市→新竹縣、苗栗市與頭份市→苗栗縣、彰化市與員林市→彰化縣、南投市→南投縣、斗六市→雲林縣、太保市與朴子市→嘉義縣、屏東市→屏東縣、宜蘭市→宜蘭縣、花蓮市→花蓮縣、臺東市→臺東縣、馬公市→澎湖縣。
4. 其他情況回傳 `None`。

### 明細欄位

- `invoices.py`：每筆明細新增 `district`（字串或 `null`），代表**賣方地址**所在的區。完整地址與統編仍不保存。
- `demo.py`：每家示範店家指定一個真實的行政區，店名維持虛構。
- 報告頁明細表新增「行政區」欄，`null` 顯示為「未知」。
- 頁尾說明改為：「頁面只保留匿名發票代碼與行政區，不嵌入原始號碼、統編或完整地址。」

## 2. 用戶標籤（`tags.py`）

### 計算基礎

- **有效品項**：金額大於 0、分類已確認（非暫定）、分類為前 10 類的明細。**同一張發票的同一品名只算一次**，不論數量或列了幾行；例如一張發票有 4 份火鍋，只算 1 項。
- **發票**：以發票代碼分組，發票金額為同張所有明細的加總（含折扣）。金額大於 0 的發票才計入。
- **可能多人的發票**：同一張發票中，任一正金額品項的數量至少 2，或同一品名出現兩行以上。這類發票不列入消費檔次，但仍計入品牌與地區。
- **非實體賣方**：賣方名稱含 `remote_sellers` 關鍵字（網購、外送、電信、水電等）的發票，地址多半是公司登記地址，不計入地區。
- 一張發票的行政區與品牌，由該張發票的賣方決定。

### 標籤定義

| 標籤 | 計算方式 | 顯示例子 |
|---|---|---|
| 品類偏好 | 有效品項至少 10 筆時，依分類計數取占比前 2 名；不足 10 筆時不產生，且品類視為不可比較 | 常買飲品（31%） |
| 常消費地區 | 排除非實體賣方後，依發票張數排序行政區，取前 2 名，每區至少 2 張；有地區的發票少於 3 張時不產生 | 高雄市苓雅區 |
| 常去品牌 | 依品牌表比對賣方名稱，出現 3 張以上的品牌 | 7-ELEVEN（12 次） |
| 消費檔次 | 排除可能多人的發票後，發票金額的中位數：未滿 150 元為小資型，150 至未滿 400 元為均衡型，400 元以上為享受型；剩下的發票少於 3 張時不產生 | 均衡型 |
| 葷素紀錄 | 見下方「葷素紀錄」 | 素食品項較多 |

所有門檻、級距與文字都放在 `configs/tags.json`（葷素紀錄的三種文字寫在程式中）。

### 非實體賣方（`remote_sellers`）

富邦媒體、網路家庭、蝦皮、酷澎、博客來、富胖達、優食、中華電信、台灣大哥大、遠傳電信、台灣電力、台灣自來水。比對方式同品牌表，可自行增補。

### 葷素紀錄

- 只看分類為正餐、飲品、零食甜點、生鮮食材的有效品項。
- 判斷順序：
  1. 品名含**明確素食詞** → 素（0）：素食、全素、蛋奶素、奶蛋素、五辛素、植物肉、蔬食、素肉、素料、素雞、素鴨、素火腿、素香腸。
  2. 否則含**葷食詞** → 葷（1）：豬肉、牛肉、雞肉、雞腿、雞排、雞塊、雞柳、羊肉、鴨肉、鵝肉、鮮蝦、蝦仁、鮭魚、鯛魚、鮪魚、鱈魚、魚排、海鮮、排骨、培根、火腿、肉燥、肉絲、肉片、肉鬆、香腸、叉燒、燒肉、滷肉、魯肉、牛排、豬排。
  3. 其他 → 未知，不計入。只寫「蔬菜」的品名（例如蔬菜水餃、蔬菜箱）屬於未知，因為無法保證整份不含肉。
- 例子：「全素香腸」「素食雞排」為素；「蔬菜豬肉水餃」為葷；「牛奶」「肉桂捲」為未知。
- 葷食比例＝葷品項數 ÷ 有判斷結果的品項數。有判斷結果的品項少於 3 個時，不產生標籤。
- 標籤描述購買紀錄：比例 0.3 以下為「素食品項較多」，0.7 以上為「葷食品項較多」，其餘為「葷素品項都有」。

### 個人檔案結構

```python
{
  "item_count": 97,                      # 去重後的有效品項數
  "category_counts": [int] * 10 | None,  # 有效品項不足 10 筆時為 None
  "top_categories": [0, 1],
  "district_shares": {"高雄市苓雅區": 0.6},
  "areas": ["高雄市苓雅區", "高雄市新興區"],   # 常消費地區
  "brand_shares": {"7-ELEVEN": 0.5},
  "frequent_brands": [("7-ELEVEN", 12)],
  "price_level": 0 | 1 | 2 | None,
  "meat_ratio": float | None,
  "flavor_items": {"示範水餃館": {"示範鮮蝦水餃": 4}},
  "tags": [{"dimension": "常消費地區", "text": "高雄市苓雅區"}],
}
```

- `flavor_items` 依品牌記錄有葷素判斷結果的品名與次數，用來產生同店差異說明。
- 地區或品牌的發票少於 3 張時，對應的占比為空集合。

## 3. 配對（`matching.py`）

### 各面向相似度（0 到 1）

| 面向 | 算法 | 權重 |
|---|---|---|
| 品類 | 兩人品類筆數的餘弦相似度 | 0.35 |
| 常消費地區 | 行政區占比的交集：每區取兩人較小的占比後加總 | 0.30 |
| 品牌 | 連鎖品牌占比的交集，算法同常消費地區 | 0.15 |
| 葷素紀錄 | 1 −｜兩人葷食比例的差｜ | 0.10 |
| 消費檔次 | 同級為 1，差一級為 0.5，差兩級為 0 | 0.10 |

### 可比較條件

- 兩人的**品類**都必須可比較（各自有效品項至少 10 筆）。
- 除了品類，品牌、葷素紀錄、消費檔次至少還要有一項兩人都有資料。
- 不符合時，這組不比較，也不會出現在名單中。常消費地區不算在這個條件裡。
- 「我」本身沒有品類資料，或品牌、葷素紀錄、消費檔次三項都沒有時，配對頁顯示「資料不足」與目前的有效品項數。

### 分數

- 符合可比較條件後，缺資料的面向不計分，其他權重依比例放大。
- **品味分數**：品類、品牌、葷素紀錄、消費檔次加權，不含常消費地區。
- **總分**：五個面向全部加權，用來排序。
- 權重放在 `configs/tags.json`。分數以四捨五入（0.5 進位）的整數百分比顯示與比較。

### 候選名單與推薦門檻

- Python 產生**候選名單**：可比較、且品味分數至少 70% 的虛構用戶，依總分由高到低排序（同分時比較品味分數，再比較名稱），附上每人的常消費地區。
- 配對頁再套用推薦門檻（`match-filter.js`）：
  - 品味分數至少 80%，推薦。
  - 品味分數 70%–79%，且對方的常消費地區包含使用者**勾選確認**的生活圈之一，推薦。
  - 使用者沒有勾選任何生活圈時，只用 80%。
- 虛構用戶的常消費地區視為他們已確認的生活圈。
- 顯示前 5 名，並顯示「符合條件 N 位」。勾選或取消勾選時即時更新。
- 沒有人符合時顯示「目前沒有夠相似的人，多掃幾張發票再看看」。

### 配對理由（最多 3 條）

只列兩人確實重疊的部分，依該面向的「權重 × 相似度」由高到低選：

- 常消費地區有重疊：「都常在高雄市苓雅區消費」
- 常去品牌有重疊：「都常去示範茶屋」
- 品類前 2 名有重疊：「都很常買飲品」
- 葷素紀錄標籤相同：「都買比較多素食品項」、「都買比較多葷食品項」或「葷素品項都有買」
- 消費檔次相同：「消費檔次都是均衡型」

一條都沒有時顯示「整體消費比例相近」。每位候選人另列出這次比較了哪些面向。

### 差異說明

兩人都有葷素紀錄，且葷食比例相差 0.6 以上時，加一條差異說明：

- 兩人有共同常去品牌，且在該品牌各有判斷得出葷素的品項，兩邊最常買的品項一素一葷：「都常去示範餐坊，但點的不一樣（示範蔬食餐盒／示範鮮蝦餐盒）」。
- 否則：「購買紀錄不同：一位素食品項較多、一位葷食品項較多」。

## 4. 虛構用戶（`personas.py`）

- 以固定亂數種子產生 40 位虛構用戶，每次結果相同。
- 8 種類型，每種 5 位：咖啡上班族、手搖學生、健身族、自己下廚、3C 玩家、旅行族、零食夜貓、家庭採買。
- 每種類型設定偏好的品類、行政區、連鎖品牌、品項與發票金額範圍；同類型成員之間有隨機差異。
- 每人 2 個月的明細，欄位與報告明細相同。
- 名稱寫出類型，例如「咖啡上班族 A」，避免像真人。
- 刻意安排的情境：
  - 手搖學生中，3 位在示範餐坊買蔬食餐盒、2 位買鮮蝦餐盒，用來展示同店差異說明。
  - 3C 玩家和示範版的「我」同在高雄市苓雅區，但品味完全不同，不會成為候選人。
  - 健身族的品味分數與「我」介於 70% 與 80% 之間，且常在高雄市苓雅區消費：勾選生活圈前不推薦，勾選後才推薦。
- 示範版的「我」是現有的虛構示範資料；私人版的「我」是使用者本人的資料。兩者都和這 40 位比較。

## 5. 配對頁（`match.html`）

- 報告頁上方「比較跟朋友品味差多少」旁，新增「找到同好 ↗」連結（`#match`）。
- 沿用朋友比較頁的做法：配對頁原始碼以 `<template>` 嵌入報告檔，切到 `#match` 時才載入到 iframe。`taste-navigation.js` 擴充為可切換兩個頁面。報告仍是可離線開啟的單一檔案。
- 頁面內容：
  1. 返回消費洞察的連結、標題、說明「配對對象是 40 位虛構示範用戶」。
  2. 我的標籤卡。
  3. **確認生活圈**：列出我的常消費地區，每個都有勾選框，預設不勾。說明「依發票賣方地址推測；勾選真的是你生活圈的地方，同生活圈的人門檻從 80% 降到 70%」。

  5. 資料不足時，以「資料不足」說明取代名單。
  6. 可展開的「怎麼算的」：面向、權重、門檻、可比較條件，以及「只用行政區與連鎖品牌，不顯示分店、日期或金額」。

## 7. 測試計畫

Python（`unittest`，全部使用虛構資料）：

- `address`：郵遞區號、台與臺、全形空白、直轄市與縣的區名結尾、縣轄市補縣名、「臺灣省」前綴、無法解析。
- `invoices`：明細多出 `district`；完整地址與統編不在輸出中。
- `tags`：有效品項去重（同張同品名只算一次）、品類需 10 筆、各標籤門檻、暫定分類與折扣排除、非實體賣方不計地區、品牌比對（含台與臺）、可能多人的發票不計入消費檔次、資料不足時不產生標籤。
- 葷素：「全素香腸」「素食雞排」為素；「蔬菜豬肉水餃」為葷；「蔬菜水餃」「牛奶」「肉桂捲」為未知；判斷結果少於 3 個時不產生標籤。
- `matching`：各面向數值、可比較條件（含「兩人各 3 張未分類發票」不可比較）、缺資料時重新分配權重、候選名單的 70% 下限與排序、理由、比較面向、差異說明。
- `personas`：結果可重現；每位用戶的第 1 名都是同類型；同店不同餡會產生差異說明；同區但品味不同的 3C 玩家不是候選人；示範的「我」至少有 1 位 80% 以上、至少 1 位 70%–79% 且地區重疊。
- 產生報告：配對頁有嵌入、沒有外部資源、不含完整地址與統編、私人版資料不足時 `ready` 為假、重複產生結果相同。

Node（`node:test`）：

- `match-filter`：沒勾選時只用 80%；勾選且地區重疊時 70% 起推薦；地區不重疊不放寬；保留原本排序。
- 現有測試全部通過；`taste-navigation.js` 的修改不影響朋友比較頁。

## 8. 不在這次範圍

- README 與簡報更新（1–3 完成後另外處理）。
- 時間節奏標籤（發票只有日期，且已決定不做）。
- 甜度、辣度（發票品名很少出現）。
- 把發票標成「幫別人買」的手動功能（幫家人買的品項無法從發票分辨，之後再做）。
- 儲存勾選的生活圈。
- 後端、帳號、真實用戶之間的配對。

## 9. 風險

- **門檻**：品類分布在人與人之間本來就相似，餘弦相似度容易偏高；校準時，同類型 160 組全部通過，不同類型 1,400 組中有 44 組在確認生活圈後通過（手搖學生與健身族、自己下廚與家庭採買，都是同店同區的組合）。
- **非實體賣方清單**：只能排除已知的網購、外送、電信與水電賣方；其他使用公司地址的發票仍可能被算進常消費地區，所以生活圈必須由使用者確認。
- **多人消費**：以「同品項 2 份以上」判斷，會把一個人買多份（例如論顆賣的水餃）的發票也排除在消費檔次外；寧可少算，也不誤判。
- **品牌名稱**：品牌表只放有把握的公司名稱，仍可能有遺漏或改名，可自行增補。
- **葷素詞典**：關鍵字判斷會有漏判，例如「高麗菜水餃」沒有標示葷素；未知的品項不計入，不會被硬判成素或葷。
